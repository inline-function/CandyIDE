## 函数

### 函数的上下文列表

回顾函数的语法

```
fun 函数名[理论参数](实际参数)<上文> : 返回类型<下文>
```

理论参数分为**类型参数**和**理论命题参数**

+ 类型参数用单大写字母表示（T）

+ 理论命题参数用小写字母表示（如 `p`）；它的全称量词写作 `∀@p`（`@` 前缀在量词里标记命题参数，与值参数区分）

实际参数就是表达式层面的参数

上文表示函数调用需要的命题

下文表示函数调用后为后面注入的命题

上文一般不显式传入，但允许

具有理论命题参数的函数叫**"超越函数"**

## 调用函数

```
f[Nat,p](91,"abc")<a = 0>
```

调用函数如上展示

对于非超越函数，类型参数和上文参数一般不需要写出来，编译器会自动推导。

编译器会自动推理函数的类型参数，

同时会自动为函数注入当前上下文中它需要的上文。

如下情况时需要显式标注：

+ 是超越函数

+ 无法推导类型参数

+ 无法自动注入上文

### 伴生命题

在上下文中，函数会自动生成一个同名命题，这个命题是函数的**伴生命题**。

规定：从伴生命题可以推出函数的下文

比方说：

```
fun f() : <p>
```

函数f的伴生命题是f<>，我们规定`f<> → p`

| 对象 | 名称             | 作用                                              |
| ---- | ---------------- | ------------------------------------------------- |
| f    | 函数的本体       | f是个表达式，上述示例中f的类型是`() => <p>`       |
| f()  | 函数的调用返回值 | f()是函数的返回值，也是表达式，上述示例中是`Null` |
| f<>  | 函数的伴生命题   | f<>是一个命题，我们规定`f<> → p`                  |

`f(91, "abc")` 的伴生命题是 `f<91, "abc">`

## 命题

### 内置命题

内置命题是编译器内置的命题，它们涉及类型与命题，并且有自己的优先级。

| 名称 | 命题  | 表述         |
| ---- | ----- | ------------ |
| 蕴含 | p → q | 若 p 则 q    |
| 等价 | p ↔ q | p 当且仅当 q |
| 否定 | ¬<p>  | 非 p         |
| 合取 | p ∧ q | p 且 q       |
| 析取 | p ∨ q | p 或 q       |
| 为   | e : T | e 具有类型 T |

### 自定义命题

命题是可以自定义的，很多常见命题都是自定义的，它们通常只涉及表达式和表达式之间的关系，不涉及类型与命题。比方说`= ≤ ≥ ∈`。

使用def定义一个命题

```
def =<a,b>
```

可以在后面添加↔表示某命题等价于某命题

```
def ≠<a,b> ↔ ¬<a = b>
```

目前尚不支持像内置命题那样对类型和命题的命题，命题只能包含表达式。

自定义命题不约束参数的类型，意思是，你可以写出某些荒谬的命题。

```
1 ∈ 2
"ok" ≥ 0
```

只是你构造不出来而已，除非你使用unchecked。

### 上下文中的表达式

在上下文中可以写表达式，可是上下文是编译期的东西，和运行期的表达式有什么关系？

上下文中的表达式写成这样你可能会想很久很久

`print(1 + 2)`

但是它其实是这样的

`FunctionInvoke(print,+(1,2))`

表达式在上下文中不运行，也不能运行，它只表示结构

结构相同的表达式就认为它们相同

`1 + 2 = 1 + 2`

不同的话不能直接认为相同，需要证明（大部分是自动证明）

`1 + 2 = 2 + 1`？

不止函数有**纯度**，实际上可以说表达式都有纯度，纯的表达式叫做纯表达式，比方说`1 + 1`，不纯的表达式例如`print("ok")`。

如果表达式不纯，则不能直接通过结构相同认为它们相同

`print("ok") = print("ok")`？

纯函数有自然命题pure，其实不止函数，lambda表达式也行，因为函数的名字本身指代的就是这个函数本身----一个函数类型的变量。故此，lambda也可以被证明pure，看如下：

`pure<f>``pure<{ 1 + 1 }>`

### 自然命题

编译器自动规定与赋予的命题，叫做**自然命题**

比方说声明一个变量

`var n = 0`

此时编译器会为当前上下文自动注入`n : Nat``n = 0`

其他不再赘述，或未来继续补充。

### 量词

语言支持使用量词，量词使用∀∃。

```
∀ x . x ∈ list → p<x>
∃ x . x : Nat ∧ x = 0
```

函数本身就是一种全称量词的构造法

```
fun f(x) : <x ∈ list → p<x>>
```

还记得自然命题吗，声明这个函数的时候，编译器会自动注入一个自然命题：

`∀ x . x ∈ list → p<x>`

存在量词的构造也很简单，只需要找到一个元素，说它有某个命题即可。

```
∃ x = 0 . x : Nat //这行写在程序里，是一句语句，不要误会是在上下文中写哦
```

于是我们就证明了

`∃ x . x = 0 ∧ x : Nat`

## 结构体

不仅函数可以携带命题，结构体也可以携带它的伴生命题

```
struct A(n : Nat)<n > 0>
```

```
//需要证明A(1).n > 0
A(1)
```

结构体作为函数参数的时候自动注入伴生命题

```
fun f(a : A){
    //a.n > 0
}
```

## 内联标识

常见的内联标识有

+ 函数的参数名称以及\$n

+ 指代函数返回值的\$

+ 指代函数本体的this

+ 指代结构体本体的self

+ 结构体的属性名称

比方说

```
impl F for A {
    fun f() : p<self> {...}
}
```

这个时候有个类型为A的a变量

```
a.f() //证明命题p<a>，这里self被内联成a了
```

## 自动证明

凝华采用的自动证明逻辑大致如下：

首先收集代码块中出现的一切表达式，优先内，其次外。

比方说对于`print(1 + 2)`，我们能收集到`print(1 + 2)``1 + 2``1``2`

我们称它们为**关键表达式**

然后尽可能的通过定理排列组合关键表达式们，以及一些策略（莱布尼茨替换，蕴含传播，自反，拆解定义等等），产生命题，命题中出现的表达式再收集仅关键表达式中，然后无限循环，直到超过某个回合，依旧没有证明出需要的命题的时候，就认为是证明失败（可能是需要手动证明，可能是证明过于复杂，可能就是单纯不可证明）。

比方说我们有a b两个关键表达式，还有一个`∀ a b . p<a,b>`的定理。

那么编译器会自动产生四个命题：

|     | a      | b      |
| --- | ------ | ------ |
| a   | p<a,a> | p<a,b> |
| b   | p<b,a> | p<b,b> |
