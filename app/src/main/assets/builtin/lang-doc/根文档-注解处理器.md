# 注解处理器

> 本文档由 AI 起草，由我审定修改。
> 定位：Sublimation 编译器的用户扩展点——通过 AST 变换管道，让用户在编译期扩展编译器能力。
>
> 本文档是一份草案。

## 1. 定位

注解处理器是**编译期的用户扩展点**。它让用户（或宿主）能"在编译过程中读取代码 + 产生新行为"。

**核心模型：AST 变换管道。**

```
编译器前端（词法 / 语法 / checker）
    ↓
输出一个完整的 AST
    ↓
注解处理器 1 → 新 AST
    ↓
注解处理器 2 → 新 AST
    ↓
...（按声明顺序）
    ↓
重新跑 checker
    ↓
最终 AST 丢给 codegen
```

**这个模型接近 Babel 插件、PostCSS 插件**——处理器是"AST → AST"的变换函数，链式执行。

**区别于 Java APT**（只能生成新文件，不能改 AST）和 **Rust proc-macro**（只能生成 token，不能改已解析的 AST）。

## 2. 核心契约

**五个已拍板的决定：**

| 维度         | 决定                                       |
| ------------ | ------------------------------------------ |
| AST 不变性   | **保持不可变**，处理器返回新 AST           |
| 处理后检查   | **重新跑 checker**                         |
| 处理器顺序   | **按编译器里的处理器列表（apt list）顺序** |
| 输入         | **AST + 符号表 + 类型查询**                |
| 重新检查时机 | **改完 AST 后，重新跑 checker**            |

## 3. 接口

### 3.1 处理器接口（Kotlin 侧）

```kotlin
interface AnnotationProcessor {
    /** 处理器名字——用于诊断和注册 */
    val name: String
    /** 关注哪些注解——编译器据此优化"是否调用这个处理器" */
    val interestedAnnotations: Set<String>
    /** 处理入口 */
    fun process(input: ProcessorInput): ProcessorOutput
}

interface ProcessorInput {
    /** 已检查的 AST——**只读** */
    val ast: FileAst
    /** 符号表——**只读** */
    val symbols: Symbols
    /** 类型查询：给定表达式节点，返回它的类型 */
    fun typeOf(expr: Expr): Type?
    /** 注解查询：给定声明，返回它的注解列表 */
    fun annotationsOf(decl: Decl): List<Annotation>
}

interface ProcessorOutput {
    /** 变换后的新 AST（不可变） */
    val ast: FileAst
    /** 新产生的诊断 */
    val diagnostics: List<Diag>
}
```

**关键点：**

- **输入只读** —— 处理器不能改输入 AST
- **输出新 AST** —— 处理器返回变换后的 AST
- **诊断可选** —— 处理器可以只改 AST，也可以只报诊断

### 3.2 AST 不变性

`Ast.kt` 的所有节点是 **Kotlin data class（不可变）**。处理器要改 AST 时：

- **只能创建新实例**（`ast.copy(...)`）
- 深度变换需要**递归重建整棵树**
- **编译器提供变换工具**，避免处理器作者手写递归

**变换工具（示例）：**

```kotlin
// 提供"遍历 + 变换"的辅助函数
fun FileAst.transform(block: (Node) -> Node?): FileAst {
    // 递归遍历，遇到要改的节点就用 block 的结果替换
    // block 返回 null 表示不改
}

// 提供"按类型过滤"的辅助
fun FileAst.transformDecls(block: (Decl) -> Decl?): FileAst

// 使用示例：
val newAst = ast.transformDecls { decl ->
    if (decl is FunDecl && decl.annotations.any { it.name == "MyCheck" }) {
        decl.copy(annotations = decl.annotations + Annotation("Checked"))
    } else null
}
```

## 4. 调用时机与多轮

### 4.1 一轮的流程

```
1. 跑 checker → 得到已检查的 AST + 类型信息 + 诊断
2. 按声明顺序跑所有处理器
   - 处理器 1：输入 AST + 符号表 → 输出新 AST
   - 处理器 2：输入**上一步的新 AST** + 更新后的符号表 → 输出新 AST
   - ...
3. 如果 AST 无变化 → 结束
4. 如果 AST 有变化 → 重新跑 checker → 回到第 1 步
```

### 4.2 多轮控制

- **最大轮数 5**（可配置）
- **无变化即退出**：某轮所有处理器都返回相同的 AST → 结束
- **超轮数报错**：处理器可能陷入"产生触发自己的代码"的循环

### 4.3 为什么重新检查

**处理器能改 AST** —— 它能：

- 加 `impl Show for Point`
- 改函数返回类型
- 删声明

**如果不重新检查，处理器能产生"非法代码"绕过检查。** 重新检查保证：

- **所有代码都过检查**（无论谁产生的）
- **处理器不能绕过语言设计**

### 4.4 防止无限循环

**问题**：处理器 A 生成 `@MyCheck` 标记的代码 → 处理器 A 又看到这个标记 → 又生成...

**两个防护：**

**其一，轮数上限**（5 轮）。超了报 `E-PROCESSOR-LOOP`。

**其二，标记已处理的内容**。处理器可以检查"这个节点是我上一轮产生的吗"——但**编译器不强制**，靠处理器作者自律。

**我倾向"只做轮数上限"** —— 简单、足够。标记机制引入"哪一轮产生的"元信息，复杂度高。

## 5. 处理器顺序

**按编译器里的处理器列表（apt list）顺序执行。**

```kotlin
// 注册接口（Kotlin 侧）
val compiler = Compiler()
compiler.addProcessor(MyProcessor1())
compiler.addProcessor(MyProcessor2())
compiler.addProcessor(MyProcessor3())
```

**顺序即声明顺序** —— 处理器 A 在 B 之前执行，A 的产出是 B 的输入。

**为什么是"声明顺序"而不是"自动拓扑排序"**：

- **最简单、最可预测**
- 用户自己控制顺序，编译器不猜
- 依赖关系由用户负责（在文档里写"我的处理器要在 X 之后"）

**命令行 / settings 注册（用户视角）：**

```
// project.settings
processor com.example.MyProcessor
processor ./plugins/my-processor.jar
```

**按行序执行。**

## 6. 输入接口

### 6.1 三种信息

**AST**：

- 完整的语法结构
- 已检查（类型标注已填充）
- **只读**

**符号表**：

- 所有声明的登记
- 类型/函数/结构体/枚举/类型类/impl
- **只读**

**类型查询**：

- `typeOf(expr)` —— 给定表达式，返回其类型
- `annotationsOf(decl)` —— 给定声明，返回注解列表
- **只读**

### 6.2 为什么需要类型查询

**只给 AST 不够用。** 处理器做有意义的处理，需要知道"这个表达式的类型是什么"：

- "给所有 `Nat` 类型的字面量加标记"
- "检查函数返回值是否符合声明类型"
- "找出所有 `List[Nat]` 类型的变量"

**这些都需要类型信息。** 而类型信息在 AST 里不是直接可读的（checker 的推导结果在 Γ 里，不在 AST 节点上）。

**类型查询接口是"checker 结果"的暴露** —— 处理器通过它读类型。

### 6.3 符号表的暴露程度

**暴露"查询接口"而非"内部结构"：**

```kotlin
interface SymbolsView {
    fun findFunction(name: String): FunDecl?
    fun findStruct(name: String): StructDecl?
    fun findEnum(name: String): EnumDecl?
    fun findTypeClass(name: String): ClassDecl?
    fun implsFor(typeName: String): List<ImplDecl>
    // ...
}
```

**处理器只读、不写。** 处理器要"登记新东西"——通过改 AST（加声明），由重新检查处理。

## 7. 输出接口

```kotlin
interface ProcessorOutput {
    /** 变换后的新 AST（不可变） */
    val ast: FileAst
    /** 新产生的诊断 */
    val diagnostics: List<Diag>
}
```

**处理器只能做两件事：**

- **改 AST** —— 通过返回新 AST
- **报诊断** —— 通过 diagnostics 列表

**不能做的事：**

- 改符号表（符号表由重新检查重建）
- 改已有诊断（处理器不能撤销编译器产生的诊断）
- 访问编译器内部状态（只能通过 input 接口）

## 8. 边界

**处理器只扩展，不改语言语义。**

| 允许                                      | 不允许                            |
| ----------------------------------------- | --------------------------------- |
| 加新诊断（如 `@Lint` 报风格问题）         | 改类型系统规则                    |
| 生成新代码（如 `@derive Show` 生成 impl） | 改命题检查逻辑                    |
| 收集信息（如 `@Route` 收集路由表）        | 绕过纯度检查                      |
| 改注解                                    | 改 AST 节点类型                   |
| 加新声明                                  | 删已有声明（如果 checker 依赖它） |

**这个边界写进文档** —— 否则处理器会变成"绕过语言设计的手段"。

**违反边界的情况怎么处理？**

- **技术上做不到**：接口只暴露"只读"信息，处理器无法改符号表
- **语义上应该禁止**：文档里明确，违反的处理器是"用户的错"，编译器不兜底

## 9. 注册机制

### 9.1 命令行

```bash
sublimation compile project/ \
    --processor com.example.MyProcessor1 \
    --processor com.example.MyProcessor2
```

**顺序即声明顺序。**

### 9.2 settings 文件

```
// project.settings
processor com.example.MyProcessor1
processor ./plugins/my-processor.jar
processor com.example.MyProcessor2
```

**按行序执行。**

### 9.3 加载方式

- **类名**：从 classpath 加载（`.jar` 放在 classpath 上）
- **文件路径**：指定 `.jar` 或 `.class` 文件

**第一版：只支持 classpath 上的类名**（简单，用户自己配 classpath）。**第二版：支持文件路径**（更灵活）。

## 10. 错误处理

### 10.1 处理器内部错误

处理器抛异常 → 编译器捕获 → 报 `E-PROCESSOR-ERROR`，包含处理器名和异常信息。

**不因为一个处理器出错而中断整个编译** —— 但报错后继续其他处理器，最终还是失败（因为编译没成功）。

### 10.2 处理器产生的非法 AST

处理器返回的 AST 可能不符合语言规则（比如"函数没有函数体"）。

**重新检查会捕获这些** —— 走现有的诊断通道。

**所以处理器不需要"保证产出合法"** —— 编译器会检查。**这符合"处理器产出视为新代码"的原则。**

### 10.3 处理器不终止

**5 轮上限**，超了报 `E-PROCESSOR-LOOP`。

### 10.4 处理器不知道要处理什么

**处理器声明 `interestedAnnotations`** —— 编译器据此决定"是否调用这个处理器"。

**如果 AST 里没有任何处理器关注的注解** → **跳过该处理器**（性能优化）。

## 11. 与解释器的关系

**处理器用 Kotlin 写（第一版）。**

- 处理器逻辑在 JVM 上跑
- **不依赖解释器**

**第二版**：处理器可以用 Sublimation 脚本写。

- 处理器逻辑跑在解释器上
- 需要解释器支持"被编译器嵌入"
- **这是解释器的额外需求**——现在就该记录

## 12. 待定

以下条目未拍板：

1. **处理器用脚本写的支持**：第二版做，还是永远不做？
2. **变换工具的 API 形态**：`transform` / `transformDecls` / `transformExprs` 等辅助函数的完整设计。
3. **处理器能否"只在某些文件上运行"**：如"只处理 `std/` 目录下的文件"。
4. **处理器能否"看到其他处理器的产出"**：处理器 A 的输出是处理器 B 的输入——这个链式关系是否要显式声明？
5. **诊断的严重级别**：处理器能报 ERROR 吗？还是只能 WARN/HINT？
6. **`ProcessorInput` 是否暴露 Γ（上下文系统的命题）**：处理器能看到"当前作用域的命题"吗？
7. **沙箱**：第一版不做（信任模型 = 用户信任自己装的处理器），第二版做（如果处理器来自第三方）。

## 13. 与现有实现的关系

**处理器是编译器管线的新阶段**，插在 checker 后、codegen 前：

```
源 → 词法 → 语法 → checker → [注解处理器（多轮）] → codegen → JS
```

**依赖前置：**

- **`frontend` 的干净接口**（AST + 符号表 + 类型查询）
- **重新检查的能力**（checker 要能"再跑一遍"）

**这两个前置和"解释器"共享** —— 解释器也要"干净的 frontend 接口"。

**建议**：**先做 `frontend` 剥离（为解释器服务），再做处理器。**
